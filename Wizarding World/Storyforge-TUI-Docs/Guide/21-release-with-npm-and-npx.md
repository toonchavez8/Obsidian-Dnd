# Stage 21: Release with npm and npx

## Result

By the end of this stage, a player can launch the public build with:

```powershell
npx storyforge-tui
```

The npm package installs a compiled Rust binary for the player's operating system. Players do not need Rust, Cargo, or a local compiler.

The release targets are:

- Windows x64
- Linux x64
- macOS x64
- macOS Apple Silicon

## Understand the package shape

The npm package is an installer and launcher for native release artifacts:

```text
npm registry
  storyforge-tui package
    selects operating system and architecture
    installs verified native archive
    exposes storyforge command

GitHub Release
  Windows x64 archive
  Linux x64 archive
  macOS x64 archive
  macOS Apple Silicon archive
  checksums
```

Use `dist`, formerly known as cargo-dist, to generate these release assets and the npm installer. Avoid maintaining four hand-written platform launchers.

## Prepare the Cargo package

The binary crate needs release metadata:

```toml
[package]
name = "storyforge-tui"
version.workspace = true
edition.workspace = true
license.workspace = true
repository.workspace = true
description = "A data-driven terminal RPG engine"
readme = "../../README.md"
publish = false

[[bin]]
name = "storyforge"
path = "src/main.rs"
```

Keep the Rust crate private on crates.io unless you deliberately choose to publish it later. npm distribution does not require publishing a crate.

At the workspace root:

```toml
[workspace.package]
version = "0.1.0"
edition = "2024"
license = "MIT OR Apache-2.0"
repository = "https://github.com/toonchavez8/storyforge-tui"
```

## Make resources relocatable

The binary must not assume it runs from the Git repository. Resolve packaged resources relative to the installed executable or use a path passed by the launcher.

Test these cases:

- Running from the repository root.
- Running from a different current directory.
- Running from a path containing spaces.
- Running after npm installs into its cache.
- Running the installed executable directly.

The public demo campaign must travel with the release. User saves and settings belong in platform data directories, not beside the binary.

## Install and initialize dist

Install the current `dist` CLI by following its official installation instructions, then verify:

```powershell
dist --version
```

Initialize it from the workspace root:

```powershell
dist init
```

Select GitHub CI, shell and PowerShell installers if useful for direct downloads, and the npm installer. Review every generated change before committing it.

The generated configuration belongs in `Cargo.toml` or the location selected by the installed `dist` version. Use the generated schema rather than copying an old internet example.

## Configure targets and included assets

Configure these Rust targets:

```text
x86_64-pc-windows-msvc
x86_64-unknown-linux-gnu
x86_64-apple-darwin
aarch64-apple-darwin
```

Configure the npm installer and include the public runtime content:

```toml
installers = ["npm"]
targets = [
    "x86_64-pc-windows-msvc",
    "x86_64-unknown-linux-gnu",
    "x86_64-apple-darwin",
    "aarch64-apple-darwin",
]
include = [
    "campaigns/academy-demo/",
    "LICENSE-APACHE",
    "LICENSE-MIT",
    "THIRD_PARTY_LICENSES.md",
]
```

Exact keys can evolve between `dist` releases. Let `dist init` create the current structure, then apply these values in that structure.

Do not include the private campaign path, authoring notes, local configuration, raw PDFs, spreadsheets, or Obsidian metadata.

## Reserve and configure the npm package

Before release, check the registry again:

```powershell
npm view storyforge-tui
```

Package availability can change. If the name is taken, choose a scoped name such as:

```text
@toonchavez8/storyforge-tui
```

The exposed binary should remain `storyforge`:

```powershell
npx storyforge-tui
npx storyforge-tui play
npx storyforge-tui validate --pack .\my-campaign
```

For a scoped package:

```powershell
npx @toonchavez8/storyforge-tui
```

Add package metadata:

```json
{
  "name": "storyforge-tui",
  "description": "A data-driven terminal RPG engine",
  "license": "MIT OR Apache-2.0",
  "repository": {
    "type": "git",
    "url": "git+https://github.com/toonchavez8/storyforge-tui.git"

    "terminal",
    "tui",
    "rust",
    "rpg",
    "game"
  ]
}
```

Prefer the package metadata generated by `dist` and change only supported fields.

## Add a release-content guard

Build the `release-audit` workspace binary in chapter 19. Do not replace it with a manual glance at `git status`.

The release workflow starts from a fresh public checkout with private submodules disabled. It copies only these allowlisted inputs into `dist/public-staging`:

- The compiled `storyforge` binary for the current target.
- `campaigns/academy-demo`.
- `LICENSE-MIT`.
- `LICENSE-APACHE`.
- `THIRD_PARTY_LICENSES.md`.

Run:

```powershell
cargo run -p release-audit -- --root dist\public-staging
```

Expected result:

```text
release audit passed: dist\public-staging
```

Only after that command succeeds may the workflow create the native archive and npm installer. Chapter 19 contains the complete audit implementation and its failure rules.

## Plan and build locally

Ask `dist` to show the release plan:

```powershell
dist plan
```

Build the host platform's artifacts:

```powershell
dist build
```

Inspect:

- Artifact names and target triples.
- Included demo files.
- Installer package metadata.
- Executable permissions on Unix archives.
- Checksums.
- Absence of private material.

If the generated npm package can be packed independently, inspect it:

```powershell
npm pack --dry-run
```

The dry-run file list is part of the release review.

## Create the GitHub release workflow

Commit the workflow generated by `dist init`. It should:

1. Trigger from a version tag.
2. Build every supported target on an appropriate runner.
3. create checksums.
4. assemble installers.
5. publish a GitHub Release.
6. publish the npm package only after artifacts succeed.

Use protected environments for npm publication. Store the npm authentication token or trusted-publishing configuration in GitHub's secret or identity system, never in the repository.

Enable two-factor authentication on the npm owner account. Limit the package's maintainers and review changes to release automation carefully.

## Use a release checklist

Before tagging:

```powershell
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo doc --workspace --no-deps
cargo run -p storyforge-tui -- validate --pack campaigns\academy-demo
cargo run -p release-audit -- --root dist\public-staging
dist plan
```

Also confirm:

- The working tree is clean.
- The changelog describes player-visible changes.
- Save migrations cover every supported older version.
- The version is consistent across release metadata.
- The public demo completes from a clean save.
- License and attribution files are current.
- The exact SRD edition used for spell slots, flexible casting, and named metamagic is identified in `THIRD_PARTY_LICENSES.md`.
- The release does not silently mix rules from different SRD editions.
- The private-content guard passes.
- The workflow uses a clean public checkout and never fetches a private repository.
- The package name still belongs to the intended npm owner.

## Tag and publish

Use semantic versions:

```powershell
git tag v0.1.0
git push origin v0.1.0
```

The generated workflow should build and publish from the tag. Do not build official archives from an uncommitted local tree.

Watch the workflow through completion. If any target or smoke test fails, fix the issue and create a new version. Do not move an already published tag.

## Smoke-test like a new player

Use clean Windows, Linux, Intel macOS, and Apple Silicon macOS environments. Test:

```powershell
npx storyforge-tui --version
npx storyforge-tui doctor
npx storyforge-tui play
```

Then:

1. Create a character.
2. Complete the branching check.
3. Finish the short duel.
4. Save and quit.
5. Launch with `npx` again.
6. Resume the save.
7. Confirm terminal restoration after normal exit.

Also test a narrow terminal, a path with spaces, no network after installation, and a non-repository working directory.

## Version the engine, content, and saves

Track three related versions:

```text
Application version: 0.1.0
Content schema version: 1
Save schema version: 1
```

The application version follows semantic versioning. Content and save schemas use integers with explicit migrations.

A patch release may fix dialogue or layout without changing schemas. A content-schema change requires pack compatibility checks. A save-schema change requires a migration before release.

## Recover from a bad release

If a release has a serious defect:

1. Deprecate the affected npm version with a clear message.
2. Keep the GitHub artifacts for investigation unless they contain private data.
3. Publish a fixed patch version.
4. If private data was exposed, remove accessible artifacts, rotate affected credentials, document exactly what escaped, and review release guards.
5. Never reuse the compromised version number.

Do not automatically delete player saves during recovery. Offer a backup and migration path.
